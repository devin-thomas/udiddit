Schema Design

The redesign addresses duplicated text entities, comma-separated votes, and flat comments. The new model adds real constraints, intentional foreign-key behavior, and indexes shaped around moderation, lookup, activity, and scoring queries.

What the redesign fixes

  • Entity duplication: usernames and topic names move into dedicated tables with uniqueness enforced.
  • Votes in first normal form: each vote becomes a row, making one-vote-per-user enforceable.
  • Thread-ready comments: comments gain a self-reference for nested replies.

Schema at a glance

Deletes cascade where content should disappear together, and user references fall back to NULL where dissociation is preferred.

usersUnique usernames and optional last-login tracking
topicsUnique topic names and optional descriptions
postsExactly one URL or text body
commentsSelf-referential threads scoped to a post
votesOne row per user-post vote

Migration Strategy

The migration follows the dependency chain of the new model: users first, then topics, posts, comments, and votes. That order keeps foreign-key references valid and preserves the original post and comment IDs.

Why the order matters

  • Users first: authors, commenters, and vote participants are unified before dependent rows are inserted.
  • Topics before posts: posts resolve topic IDs through the normalized topics table.
  • Votes last: votes are exploded from old comma-separated text fields after posts and users exist.

Data-quality tradeoff documented explicitly

The supplied dataset contains 152 legacy titles longer than the stated 100-character product rule. Instead of truncating source data, the final schema stores titles up to 150 characters and documents that mismatch in the supporting report.

That keeps the migration lossless while making the discrepancy explicit in the project documentation.

Validation Story

The project includes a dedicated validation script and example DQL set so users can confirm counts, integrity rules, and query behavior without digging through the migration by hand.

What was checked

  • Users, topics, posts, comments, and votes match expected totals after migration.
  • Every migrated post contains either a URL or text content, but never both and never neither.
  • Votes are restricted to 1 and -1, with duplicate non-null user votes rejected.
  • The repo includes a three-level nested JSON comment-tree query.

Verified totals

  • 11,077 users unified from post authors, comment authors, and vote participants.
  • 89 topics normalized from repeated topic-name text values.
  • 50,000 posts / 100,000 comments preserved with original identifiers.
  • 499,710 votes exploded from denormalized upvote and downvote text columns.

Run It Locally

The repo now includes Docker Compose and Make commands so users can run the PostgreSQL migration and validation flow without manually configuring a local database. 

docker compose up -d
make reset-db
make validate
